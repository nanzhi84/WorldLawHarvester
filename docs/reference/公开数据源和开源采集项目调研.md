# 全球法律与财税公共数据源及开源采集项目调研

> 核验日期：2026-10-17（Asia/Shanghai）<br>
> 核心问题：**数据从哪里获取、用什么方式获取、能否持续更新、哪些开源采集代码值得借鉴。**<br>
> 判断原则：公开可访问，不等于允许自动采集；允许内部使用，不等于允许全文展示、下载或再分发；采集器代码开源，不等于其上游数据可商用。

# 调研结论（先读）

- **数据怎么获取：** 优先使用政府、法院和税务机关提供的接口或整批下载文件；没有下载渠道的，再从官方网站定期采集；官方资料仍有缺口时，再向商业平台购买允许长期保存和使用的数据。
- **目前可以直接获取：** 台湾、日本、欧盟、英国、德国、西班牙、瑞士、美国、加拿大和澳大利亚可通过程序读取官方数据。
- **目前还不能稳定获取：** 中国及多数亚洲法域仍以网页查询为主；中国裁判文书网、越南法规和裁判网站、印度及泰国部分司法或公报网站存在验证码、访问限制或许可要求，需要另行申请接口、数据文件或书面授权。
- **开源项目能做什么：** 目前没有一个开源项目可以直接、完整地采集全球法律数据。Laws.Africa CLI 需要先购买数据服务；Juriscraper、oldp-ingestor、Open States、OpenCaseLaw 和 World Wide Law 可节省部分开发工作，但必须逐个网站测试后才能使用。在github和Hugging Face有部分法域的法律数据，但是覆盖和时效性无法保障，可以选择部分用来初始化数据。
- **商业数据库怎么用：** 在数据建设初期无法覆盖所需数据范围时，通过商业数据库来提升必要数据的覆盖度。
- **本报告的覆盖范围：** 已经检查既定重点和扩展法域，但还没有逐一覆盖美国各州、加拿大各省、澳大利亚各州、德国和瑞士的地方层级，以及非洲所有国家。
- **阅读指引：** 可重点查看 1.3、2.2、2.3、3.0、4.1章节

# 一、调研背景与目标

## 1.1 调研背景

建设全球法律与财税数据库，首先要解决的不是检索或生成能力，而是能否持续取得权威、完整、可追溯的原始数据。全球法律与财税资料分散在官方 API、批量数据包、政府网站、法院门户、税务机关解释库、第三方平台和开放数据集中；不同渠道在覆盖范围、更新频率、访问限制和商业使用权上差异明显。

因此，需要同时建立两张清单：一张说明“可以从哪些数据源获取什么数据”，另一张说明“哪些开源采集项目的适配器、增量机制和输出模型可以复用”。
## 1.2 调研目标

- 建立全球法律与财税数据源清单，明确法域、数据类型、获取方式、更新机制和当前可接入程度；
- 建立经过代码核查或本地测试的开源采集项目清单，具体说明其真实采集对象、适配器范围、全量/增量能力和输出；
- 识别自动采集、商业使用、持久存储、全文展示、下载和再分发的许可边界；
- 形成以数据获取为中心的接入顺序和持续更新方法，为全球法律与财税数据库建设提供可执行的来源底账。

## 1.3 调研范围

**重点法域：** 中国大陆、台湾、越南、马来西亚、印度尼西亚、澳大利亚、日本、新加坡、欧盟、英国、美国、加拿大。

**扩展法域：** 韩国、泰国、菲律宾、印度、新西兰、德国、法国、西班牙、瑞士、非洲多法域及国际组织。

**数据类型：** 法律法规、行政规章、司法解释、裁判文书、官方公报、财税政策、税务裁定与解释、法律修订、历史版本、废止替代和引用关系。

“当前可用性”统一使用四种结论：

| 结论 | 判定标准 |
|---|---|
| **可直接采集** | 已取得机器可读样本或确认公开 bulk，可直接进入接入开发 |
| **需适配验证** | 官方入口可用，但仍需申请 key、编写网页适配器或验证全量/增量边界 |
| **采集受阻** | 实测出现 WAF、验证码、403、DNS 失败、超时或其他自动访问障碍 |
| **仅人工或授权** | 条款、付费或书面许可要求不允许将公开检索等同于批量建库 |

技术上能够下载，不代表允许商用、长期保存或再分发；这两类结论在各数据源行中分别说明。

# 二、公共数据采集渠道分类

## 2.1 官方法律与财税数据源

官方来源是主数据源，应按以下优先顺序接入：

| 优先级 | 渠道 | 适用场景 | 获取与更新方式 |
|---|---|---|---|
| 1 | 官方批量下载 | 首次回填、周期全量对账 | XML/JSON/ZIP/CSV 数据包；保存包版本、发布时间和校验和 |
| 2 | 官方 API | 日常增量、版本查询、精确回补 | 按游标、更新时间、发布日期或标识符增量；保留请求和响应证据 |
| 3 | 官方 RSS/Atom/公报目录 | 新增发现和变更监测 | 订阅增量后回到官方详情页或附件取原件 |
| 4 | 官方公开网站 | 无 API/批量渠道时补齐 | 低频、限速、条件请求；不绕过登录、验证码、WAF 或访问控制 |
| 5 | 官方人工申请/授权 | 批量能力未公开但价值高 | 申请数据接口、数据包或书面许可，明确缓存和再分发范围 |

法律法规、判例和财税解释应分开采集。法规关注公布、生效、修订和失效；判例还要处理更正、撤回、密封和重新匿名化；税务解释需记录税种、适用事实、适用期间以及被替代或撤销状态。

## 2.2 第三方法律数据平台与商业法律数据库

“第三方平台”是指不是法律、裁判或税务解释原始发布机关的平台；“商业法律数据库”是其中以付费订阅、出版社内容或编辑增值服务为主的一类。两者有交叉，但不是同一个分类维度。同一品牌可以同时提供网页订阅和另行签约的 API/data feed；必须按“具体产品 + 合同权利”判定能否用于建库。

### 2.2.1 与官方数据源的关系

| 层级 | 主要产品形态 | 对自建数据库的价值 | 默认权利判断 |
|---|---|---|---|
| 官方原始源 | 政府/法院 API、bulk、公报、官方网站 | 权威原文、版本和公布时间基线 | 优先作为主数据源；仍需核对开放许可、网站条款和个人信息限制 |
| 公益/开放聚合平台 | 免费检索、有限 API、开放数据集 | 来源发现、历史回填、跨库 QA，以及部分平台的批量数据 | 免费访问不等于允许系统性下载；必须看平台条款和子来源权利 |
| 商业数据交付服务 | 合同 API、bulk、replication、feed、MCP | 补齐难获取法域、结构化字段、引证关系、翻译和更新监测 | 只有合同明确允许自动获取、持久存储和目标用途时，才是可用的采购型数据源 |
| 商业订阅检索库 | 按席位/模块订阅的检索网页 | 编辑摘要、有效性、修订沿革、citator、授权 law reports、翻译和评论 | 默认仅供授权用户研究；不得将账号交给采集器，也不得重建可替代原产品的数据库 |

官方源承担原文与版本基线；商业库主要承担覆盖缺口、引证与有效性判断、英文翻译、二次文献和质量核验。只有另行采购数据交付协议后，商业库才能成为自建库的上游数据源。

### 2.2.2 跨法域及垂直领域商业数据平台

本节只保留不能合理归入单一国家商业法律数据库、且主营跨法域数据交付或垂直监管情报的产品。API、bulk、feed、MCP 是**交付方式**，不是平台类别：威科先行 MCP、Nexis Data+、vLex API、Indian Kanoon API、Docket Alarm API、UniCourt Enterprise API 和 Laws.Africa Content API 分别并回 2.2.4 的中国、跨国、印度、美国和非洲行，在“机器接入”字段说明其可获取性；CourtListener 和 Open Law Data Thailand 按其公益/开放属性归入 2.2.3。

| 平台/产品 | 覆盖与交付能力 | 收费/访问模式 | 建库使用判断 |
|---|---|---|---|
| [Legal Data Hunter](https://legaldatahunter.com/) | 多法域法律检索、全文、引用及 API/MCP | 商业服务，采集程序有对应的开源项目 | 可做来源发现和授权补数；批量、持久存储、索引/embedding、训练和客户展示必须明示授权 |
| [FiscalNote PolicyNote](https://fiscalnote.com/) | 美国国会、50 州及多国立法/监管监测，支持 API/MCP 与工作流集成 | 企业订阅/数据合同 | 适合变动发现和监管情报，不替代官方法律原文 |
| [Compliance.ai / Archer Evolv API](https://www.compliance.ai/api/) | 美国联邦/州及部分英国、加拿大、欧盟金融监管变动；REST/RSS | 企业 API 合同 | 适合金融监管事件归一化和提醒，不是通用法律全文库 |
| [Enhesa](https://www.enhesa.com/faq) | 全球 EHS、化学品、产品合规和可持续监管；支持集成/API/MCP | 企业合同 | 适合企业合规义务库，不宜当作通用法律全文主源 |

# 三、全球法律与财税数据源清单

以下清单坚持“一行一个数据源或一个明确的数据产品”。“数据规模”只有在官方给出稳定口径时才记录数量；否则写明动态或未公布，避免用不可靠估算误导容量规划。

每个法域必须逐项核查正式公报、现行及历史法规、普通裁判文书、判例/司法解释、财税监管解释和修订引用关系；未找到的类型直接标明“尚未确认”，不能用法规网站代替案例网站，也不能写成已经完整覆盖。

本轮复核增加一项法域完整性门槛：不能因为已经找到法规数据库或政府文件门户，就判定该法域的官方渠道已经覆盖。每个法域至少要分别核查 **正式公布载体（Gazette/Journal/Register）**、**合并/现行法与历史版本库**、**司法裁判源**、**税务/监管解释源**，并说明它们之间的权威关系。此前漏列越南电子公报的直接原因，就是来源发现偏重 API、结构化数据库和合并文本，没有把“正式公布载体”设为逐国必查项；同类缺口也出现在中国大陆、台湾、日本、韩国、新加坡、印度、英国、新西兰和南非。

LDH / World Wide Law 可用于发现候选网站和复用适配器，但不能代替官方核验：例如其 `VN/CongBao` 适配器帮助定位了越南电子公报，而日本官报、韩国电子官报、新加坡 e-Gazette、新西兰 Gazette 等仍需从各国官方发布体系反向补齐。

越南需要明确区分四类官方来源：`vbpl.vn` 是国家法律规范性文件数据库，`congbao.chinhphu.vn` 是电子公报，`congbobanan.toaan.gov.vn` 是普通裁判文书/决定公布门户，`anle.toaan.gov.vn` 是最高人民法院选定公布的判例门户。法规库不能替代案例库，判例门户也不是全部裁判文书库。旧入口 `vbpl.moj.gov.vn` 于 2026-10-17 经公共 DNS 查询已无解析记录，报告不再把它列为生产入口。

## 4.3 项目筛选与数据获取方案

### 4.3.1 推荐顺序

| 层级 | 建议采用内容 | 原因 | 进入下一阶段的门槛 |
|---|---|---|---|
| 第一层：直接接入 | 台湾 XML、e-Gov、EUR-Lex/CELLAR、legislation.gov.uk、法国开放数据、GovInfo/eCFR/Federal Register、Justice Laws、澳大利亚 Register | 官方、结构化、适合全量与增量，是最稳定的数据底座 | 每源取得真实样本，完成字段映射、许可快照和一次全量/增量演练 |
| 第二层：复用专项采集器 | Juriscraper、Open States、oldp-ingestor provider、OpenCaseLaw 模式 | 已有明确来源 adapter，可显著降低法院/州站开发成本 | 固定 commit；逐 adapter 连接真实源并完成至少两轮增量及删除/更正验证 |
| 第三层：借鉴适配器 | World Wide Law、OALC Creator、unitedstates/congress | 覆盖广或专项能力强，但来源状态和维护质量不一致 | 逐 adapter 做许可证、样本、限速、字段完整性、修改/删除测试 |
| 第四层：商业数据交付 | CourtListener 免费低配额层用于 PoC；LDH、Laws.Africa、Indian Kanoon、Nexis Data+、vLex API、威科 MCP、Docket Alarm/UniCourt、IBFD API 用于补缺或增值 | 只采购可交付 API/bulk/feed 和明确内容权的产品；商业检索订阅另用于 QA/编辑研究 | 合同明确自动访问、持久存储、全文展示、索引/embedding、派生数据、再分发和到期处置 |
| 第五层：解析与管理 | Bluebell/Cobalt、Indigo/OLDP、OpenFisca | 处理已经合法取得的数据 | 不得被用于证明数据获取权或来源覆盖 |

### 4.3.2 首批应建设的采集组合

1. **官方批量/API 骨架：**先用“可直接采集”的官方来源打通全量回填、增量同步、原件保全和版本关系。首批覆盖欧盟、英国、美国、加拿大、澳大利亚、日本、台湾、法国、西班牙和瑞士；其余法域按 3.0 表中的结论分别做适配、授权或受阻处置。
2. **官方公报证据层：**单独接入越南、台湾、新加坡、韩国、中国国务院、新西兰和南非公报；印度做表单型适配，日本按站点限制采用授权/受控下载，马来西亚保持候选。每条法规尽可能绑定公报名称、期号、公布日、页码/notice number 和官方 PDF 哈希，不用合并法网页覆盖公布本。
3. **重点亚洲网页适配器：**中国国家法律法规数据库、国家税务总局、印尼 BPK/JDIH/DGT、马来西亚 LOM/HASiL、新加坡 SSO/IRAS 分别做专项适配和验证。越南 VBPL 因自动请求返回 403，当前不进入生产采集清单；优先使用越南电子公报及其他已验证官方来源。每个站点独立限速、失败隔离和条款记录，不建立“万能爬虫”。
4. **判例专项链路：**美国从 Juriscraper/CourtListener/PACER 分层获取；台湾使用司法院开放 API；法国使用 Judilibre；其他无 API 法域仅在条款允许时低频采集并实现撤回/匿名化同步。
5. **财税专项链路：**财税法律、行政解释、公共裁定、FAQ/指南分层保存；所有解释文件记录税种、文号、适用期、撤回/替代关系和依据法，不把指南状态提升为法律。
6. **商业渠道分两类管理：**LDH、Laws.Africa、Nexis Data+、vLex API、Docket Alarm/UniCourt、IBFD API 等只有在取得数据交付权后才能进入采集清单；Westlaw、Lexis+、北大法宝、CLJLaw、SCC Online 等普通订阅默认只进入人工研究和 QA 清单。合同权利要落实为系统级的下载、保留、展示和删除策略。

### 4.3.3 每个数据源必须建立的获取底账

| 字段组 | 必填内容 |
|---|---|
| 来源身份 | 法域、数据类型、权威层级、官方/第三方、入口 URL |
| 获取方式 | API/bulk/web/授权、认证方式、配额、限速、费用、robots/条款证据 |
| 覆盖边界 | 起止年份、法院/机关清单、文书类型、语言、历史版本、附件范围 |
|  |
| 增量机制 | 游标、发布日期、更新频率、最后成功水位 |
| 变更机制 | 修订、替代、失效、撤回、删除 |
| 输出契约 | 原始响应、正文、附件、获取时间、source ID、哈希 |
| 使用权限 | 内部索引、摘要、全文展示、下载、API、再分发分别是否允许 |
| 运行证据 |  文档ID、失败率、最后成功时间 |

### 4.3.4 持续更新和验收

- 全量包/API 用于首次回填；之后按官方游标或修改时间增量，并保留重叠窗口；
- 网页源采用低频条件请求、缓存、重试退避和熔断，不绕过访问控制；
- 每周或每月按来源做总量、ID 集合和哈希对账，发现长期无新增时报警而不是默认为“无新法”；
- 记录“法律有效时间”和“系统获知时间”双时态，确保能回放任意日期的有效文本；
- 上线前必须取得真实数据样本；
- 验收不只看“抓到数据”，还要检查覆盖分母、重复率、缺失率、版本链、附件成功率和许可用途是否匹配。
